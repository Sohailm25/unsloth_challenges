## Issues Encountered and Resolved

1. **AttributeError: 'LlamaAttention' no 'num_heads'**
   - Cause: transformers 4.57+ changed attribute access
   - Fix: Use `self.config.num_attention_heads` instead

2. **ValueError: too many values to unpack (expected 2)**
   - Cause: Attention return signature changed
   - Fix: Return `(attn_output, None)` instead of 3 values

3. **InternalTorchDynamoError: NestedUserFunctionVariable**
   - Cause: `create_block_mask` with `lru_cache` inside compiled function
   - Fix: `@torch._dynamo.disable()` on helper functions

4. **NoValidChoicesError: flex_attention**
   - Cause: T4 doesn't have enough SMs for max_autotune with flex_attention
   - Fix: Use SDPA instead of flex_attention on T4

5. **TypeError: max_seq_length unexpected**
   - Cause: TRL 0.12+ renamed parameter
   - Fix: Use `max_length` instead of `max_seq_length`

6. **BackendCompilerFailed: 'float' object has no attribute 'meta'**
   - Cause: torch.compile tracing through PEFT's Linear4bitLt wrapper
   - Fix: Patch PEFT's `peft.tuners.lora.bnb.Linear4bit.forward` with `@torch._dynamo.disable()`

7. **RuntimeError: compiled_autograd requires no threads in backwards()**
   - Cause: compiled_autograd conflicts with multi-threaded training
   - Fix: Set `torch._dynamo.config.compiled_autograd = False`

- Received recommendations for:
  - GPU capability detection (`should_enable_flex_attention()`)
  - High-end GPU tuning (TF32, coordinate_descent)
  - Custom torch.library op pattern for NF4 dequant
  - Proper causal masks for KV cache (lower-right masks)
  - Explicit scaling in flex_attention (`scale=1.0/sqrt(head_dim)`)

### flex_attention Issues Discovered
Attempted multiple approaches, all failed in PyTorch 2.5.1:

1. **max_autotune=True** → `NoValidChoicesError: No choices to select`
2. **max_autotune=False** → Same NoValidChoicesError
3. **dynamic=False** → `RuntimeError: CUDA error: device-side assert triggered`

**Root cause**: flex_attention + torch.compile has fundamental instability issues in PyTorch 2.5.1.

### Final Decision
- flex_attention disabled by default (`should_enable_flex_attention()` returns False)
- Users can opt-in via `ENABLE_FLEX_ATTENTION=1` environment variable (experimental)
- SDPA provides compiled attention (+2 points) and works reliably on T4/A100

# Challenge C: Part A Kernel Integration Attempt (Session 8)

## description of what was run, for what purpose
- Attempted to integrate Part A NF4 kernel via torch.library custom op to avoid -2 penalty for `no_torch_compile_BnB`
- Goal: Change scoring from -2 (dynamo.disable) to +1 (Part A kernel) = 3 point improvement

### Implementation Approach
1. Registered `challenge_c::nf4_dequantize` custom op via torch.library
2. Implemented Meta and CUDA implementations
3. Added precompute function to cache NF4 metadata outside traced region
4. Updated patched_forward_custom_op to use custom op

### Issues Encountered

1. **T4: bf16 PTX not supported on sm75**
   - Error: `Feature '.bf16' requires .target sm_80 or higher`
   - Cause: Pre-quantized model from unsloth uses bf16 internally
   - torch.compile generates Triton kernels with bf16 which T4 doesn't support

2. **A100: Triton matmul dtype mismatch**
   - Error: `tl.dot dtype mismatch: fp16 @ fp16 -> f32 | ^ expected fp16`
   - Cause: Inductor fusion attempts with custom op output cause dtype conflicts
   - The matmul between dequantized weights (bf16 or fp16) and input creates issues

3. **Root Cause Analysis**
   - torch.library custom ops are visible to inductor for fusion
   - Inductor tries to fuse custom op output with subsequent F.linear
   - This creates Triton kernels with mismatched dtypes or unsupported PTX

### Decision
- Reverted to `@torch._dynamo.disable()` approach which works reliably
- Part A kernel IS used for dequantization (via dynamo.disable fallback)
- Custom op integration blocked by inductor fusion issues

### Test Results (After Revert)
| Test | GPU | Result |
|------|-----|--------|
| Graph break test | T4 | PASS |
| Training | T4 | PASS (10/10 steps, loss=2.396, 75.49s) |

### Final Scoring Assessment
- ❌ BnB via dynamo.disable: -2 points (blocked by inductor issues)
- ✅ Attention compiled (SDPA): +2 points
- ✅ MLP compiled: +1 point
- ✅ Loss compiled: avoid -1
- ✅ LayerNorms compiled: avoid -3

**Estimated Score: ~1 point** (3 points - 2 penalty)

### Files Modified
- challenges/challenge_c_solution.py - Removed custom op path, simplified PEFT patch
- modal_challenge_c.py - Added torch_dtype=fp16 for T4 compat

### Technical Notes
The torch.library custom op registration code remains in the file but is not used:
- `_nf4_lib.define()` and implementations registered
- `NF4_CUSTOM_OP_AVAILABLE = True`
- But the patching code now uses the dynamo.disable fallback

To enable custom op path in future (when PyTorch/inductor matures):
1. Fix dtype handling in Meta implementation
2. Add explicit dtype casting before F.linear
3. Consider marking op as non-fuseable

### Lessons Learned
1. torch.library custom ops work well for isolated ops but inductor fusion creates issues
2. Pre-quantized models with bf16 internal dtype need explicit fp16 handling on T4
3. dynamo.disable is the reliable fallback for complex external kernels
